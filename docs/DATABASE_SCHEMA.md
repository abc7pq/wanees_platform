# WANEES database plan

## Purpose

This document defines the durable data layer for the complete WANEES web application.

The first demo used JSON and process memory. The full web product uses PostgreSQL as the system of record. JSON remains useful for import, export, seed fixtures, and offline demo fallback.

## Database decisions

- Database: PostgreSQL.
- Migrations: Prisma migrations.
- Access: one typed repository layer; UI code never writes SQL directly.
- Validation: runtime schemas at API boundaries and database constraints underneath.
- Tenant isolation: every organizer-owned record resolves through organization and event scope.
- Visitor identity: anonymous pseudonymous sessions by default.
- Large files: object storage, with metadata and URLs in PostgreSQL.
- Search: PostgreSQL full-text search first; vector search is optional and not required for Phase 1.
- Live state: PostgreSQL event records and current snapshots first. Add Redis only when measured concurrency requires it.
- Time: store timestamps in UTC and render using the event timezone.

## Implemented foundation

The first PostgreSQL/Prisma foundation now lives in the repository:

- `prisma/schema.prisma` is the canonical relational schema.
- `prisma/migrations/` contains the initial schema and catalog runtime-config migration.
- `prisma/seed.ts` imports the Boulevard World fixture and creates a small second event for isolation checks.
- `CatalogVersion.config` stores event-specific runtime settings such as opening hours, walking speed, and crowd curve.
- `Zone.popularityWeight` and `Schedule.kind` preserve the inputs needed by the deterministic planner when a catalog is loaded from PostgreSQL.
- The visitor API exposes a published event catalog and falls back to the JSON fixture only when the database is not configured or reachable in demo mode.
- The admin app exposes a first PostgreSQL-backed event list at `/api/v1/events`; its current `ADMIN_TOKEN` guard is transitional until durable organizer auth is complete.
- `PresencePing` holds anonymous, consented device presence for crowd sensing:
  - Each row stores event, zone and a salted, hourly-rotating `deviceKey`. It never stores coordinates or the session id.
  - Rows expire after 5 minutes. `npm run db:cleanup` deletes them.
  - Aggregates of at least `WANEES_PRESENCE_MIN_DEVICES` devices become `CrowdSnapshot` rows with source `SENSOR`.
  - An active operator override still outranks sensed presence.
  - Migration `20261125170000_presence_pings`. Rollback: drop the table; the data is ephemeral.
  - See `docs/MAP_AND_CROWD_SENSING.md`.
- `PushSubscription` holds one Web Push subscription per visitor device for lock-screen nudges:
  - Created only after the visitor taps «فعّل التنبيهات» and the browser grants notification permission.
  - Stores the push-service endpoint (only known browser push hosts are accepted), the browser's encryption keys, the guide path a tap reopens, and the ids of nudges already delivered. No name, contact or location.
  - Scoped to the visit: `expiresAt` equals the session's, and the row cascades with `VisitorSession` and `Event`. It is also deleted on unsubscribe, when the push service answers 404/410, or after 5 failed sends. `npm run db:cleanup` removes expired rows.
  - Migration `20261125190000_push_subscriptions`. Rollback: drop the table. In-app nudges keep working, and devices re-subscribe on their next opt-in.
- `RouteEdge` rows for Boulevard World are generated by `packages/engine/src/walkway-graph.ts`: natural-neighbour walkways that never cross the lagoon.
- Operator updates are stored in `EventUpdate`, crowd overrides also materialize as `CrowdSnapshot`, and visitor replanning records either an immediate superseding `Itinerary` or an expiring visitor-reviewable `proposed` itinerary with source references to the live updates.
- `OrganizerSession` stores only a hash of a short-lived random session token. `User.passwordHash` uses salted `scrypt`; the seed sets it only when `WANEES_OWNER_PASSWORD` is supplied outside the repository.

### Prisma 7 local tooling

- `prisma.config.ts` owns the schema, migrations path, and CLI datasource URL.
- `prisma/schema.prisma` intentionally omits a datasource `url`; Prisma 7 reads it from the config file.
- Runtime clients use `@prisma/adapter-pg` and `pg`, so the visitor app, admin app, seed, and root tooling share the same connection model.
- `npm run db:generate` and `npm run db:validate` can run without a live database. `npm run db:migrate` and `npm run db:seed` require PostgreSQL.

## Main entities

### organizations

Represents the customer or organizer that owns one or more events.

Fields:

- id
- name
- slug
- status
- created_at
- updated_at

### users

Represents an organizer or staff account.

Fields:

- id
- email
- display_name
- password_hash or external_auth_subject
- status
- created_at
- updated_at

Visitor accounts are not stored here in Phase 1.

### memberships

Connects users to organizations.

Fields:

- id
- organization_id
- user_id
- role: owner, admin, operator, editor, analyst
- created_at

Unique constraint:

- organization_id plus user_id

### venues

Represents a physical place that can host multiple event occurrences.

Fields:

- id
- organization_id
- name
- slug
- timezone
- address
- map_asset_id
- geo_anchor_lat, geo_anchor_lng — GPS of plan point (0, 0); null until calibrated
- meters_per_unit — plan scale (Boulevard World: 0.62)
- rotation_deg — plan rotation from east, clockwise, −180..180 (default 0)
- live_guidance — live GPS guidance for visitors (default false)
- navigation_accuracy — `SURVEYED` or `APPROXIMATE` (default); approximate guides tell the visitor to follow site signs too
- gps_simulation — staff may simulate a position for demos (default false)
- created_at
- updated_at

Constraints (migration `20261127090000_venue_navigation`): the calibration is all-or-nothing,
`rotation_deg` stays within ±180, and `live_guidance` requires a calibration. Organizers change
these through `PATCH /api/v1/events/{slug}/navigation` (owner or admin), audited as
`venue.navigation_change`. The setting belongs to the venue, so it applies to every event there
and reaches visitors within the 30-second catalog cache, without republishing.

### zones

Represents an area within the venue.

Fields:

- id
- catalog_version_id
- stable_key
- name_ar
- name_en
- description
- map_x
- map_y
- capacity
- tags
- status
- review_status
- source_refs (content-source IDs for imported records)

- highlights_ar, highlights_en (short published highlights such as «جديد 2026», at most 20 each)
- entrance_node_key (optional; the stable key of an open route node in the same version and zone. Directions

- catalog_version_id plus stable_key

Content rule (audit 1.3): an ACTIVE activity needs an Arabic description and at least 3 known tags.

`20261127100000_activity_tags` adds the columns with empty defaults and a check on the sizes; rollback
is dropping the four columns (no other table depends on them).

### route_edges

`sourceId` optionally references the catalog's `ContentSource` for a surveyed travel time and distance. Draft copies remap the reference to the new version. An open segment in a field catalog needs a verified walk source before publication. Older published fixture records can keep a null reference.

Represents walkable connections.

Rules:

- The route engine uses edges, not straight-line distance.
- A directed edge is allowed for one-way routes.

### event_updates

Fields:

- event_id

Revocation is a soft state change. Keep the original update for history and

### crowd_snapshots

Stores crowd state by zone.

Fields:

- id
- event_id
- zone_id
- event_update_id (nullable; links an operator override to its crowd row)
- level
- source: simulated, operator, sensor, integration
- confidence
- observed_at
- expires_at

Never present simulated values as measured values.
When an operator update is revoked, its linked snapshot is retained for audit
and storage history but excluded from visitor live state and replanning. Deleting
an update safely detaches the snapshot rather than deleting the observation.

### visitor_sessions

Anonymous session for one event visit.

Fields:

- id
- public_token_hash
- event_id
- catalog_version_id
- locale
- entry_point
- consent_state
- assistant_context (structured IDs only)
- assistant_context_expires_at
- started_at
- last_seen_at
- expires_at
- deleted_at

Rules:

- Store only a hash of the public token.
- Pin the session to the catalog version.
- Do not use a visitor session as a cross-event identity.
- `visitor_id` and `visitor_visit_id` are set only for a registered visitor (below); both are nullable and `ON DELETE SET NULL`.
- `channel`: `web`, `call` or `kiosk` (CHECK constraint). A kiosk session is anonymous and short.
- `previously_visited`: stable activity keys from earlier visits of a remembered guest or a registered visitor,
  copied when the visit starts (at most 200). The planner leaves them out of a new plan unless the visitor asked
  for one by name, or nothing else fits; the agent brief lists them as «جرّب من قبل».

### guest_profiles (opt-in «تذكّرني»)

Anonymous, no name or phone. Created only when the visitor ticks «تذكّرني للزيارة الجاية» (unticked by default)
or opts in at session start. Scoped to one organization; the browser holds the token in the HttpOnly
`wanees_guest` cookie and the row keeps its SHA-256 hash.

- `preferences` (sanitized snapshot, refreshed on each plan), `visited_keys` (last 200), `visit_count`
  (visits started, CHECK `>= 0`), `last_visit_at`.
- A new visit with the cookie attaches the profile, counts the visit and copies `visited_keys` into
  `visitor_sessions.previously_visited`.
- Unticking «تذكّرني», «احذف بياناتي» or `DELETE /api/v1/guest` deletes the profile; sessions keep going
  (`ON DELETE SET NULL`).
- Registering (OTP verify) merges the profile into the visitor in the same transaction: visit history is merged,
  the guest's taste fills in only when the visitor has none, and the profile and cookie go.

### visitor_link_grants (phone ↔ screen)

A visitor's phone makes a 6-character code (10 minutes, one use) so a venue screen can show the plan.

- `event_id`, `session_id` (the phone's visit, cascade), `code_hash` (SHA-256 of event id and code, unique per
  event), `scope` (`read` only, CHECK), `expires_at`, `redeemed_at`, `redeemed_by_session_id` (the screen's
  session, `SET NULL`), `last_used_at`, `revoked_at`.
- A redeemed grant ends after 60 seconds without a read, on «انتهيت», when the phone revokes it, or when the
  phone's visit ends. Making a new code revokes the previous unused one.
- `db:cleanup` deletes ended grants and unused expired codes; the rest go with their session.
- Recovery: migration `20261127130000_guest_memory_link_codes` is additive. Dropping the table and the four new
  columns restores the previous schema; no other table refers to them.

### visitors, visitor_devices, visitor_visits, visitor_otp_challenges (optional registration)

Behind `WANEES_FEATURE_VISITOR_REGISTRATION` (off by default). Anonymous visits stay the default;
when an organizer turns the flag on, a visit starts only after the visitor gives a name, an SMS-verified
Saudi mobile, and explicit consent to the versioned notice (`VISITOR_CONSENT_VERSION` in `packages/contracts`).

- `visitors`: `organization_id`, `phone_e164`, `name`, `consent_version`, `consented_at`, `phone_verified_at`,
  `preferences` (sanitized snapshot), `visited_keys` (last 200 stable activity keys), `last_seen_at`.
  Unique on `(organization_id, phone_e164)`: the same number at two organizations is two unrelated visitors.
- `visitor_devices`: SHA-256 hash of the `wanees_visitor` device token only, sliding 90-day expiry.
- `visitor_visits`: one row per event visit (party, planned activity keys, rating), kept after the 24-hour session is deleted.
- `visitor_otp_challenges`: pending name and phone for 10 minutes and an attempt counter. The SMS provider
  (Twilio Verify) generates and checks the code; WANEES never stores or logs it.

Rules:

- Phone numbers appear in logs and UI only masked (`+9665•••••678`).
- «احذف بياناتي» (`DELETE /visitor/me`) removes the visitor, devices and visits in one transaction.
- `db:cleanup` deletes expired challenges and devices hourly, and visitors with no visit for
  `WANEES_RETENTION_VISITOR_DAYS` (default 365).
- Recovery: the migration is additive; dropping the four tables and the two session columns restores the previous schema.

### visitor_preferences

Fields:

- id
- session_id
- companions
- mood
- interests
- budget_max
- available_minutes
- walking_tolerance
- start_point_id

- opt_in_persist

- likes (`who:tag`, for example `son:طيران`; the tag is a controlled tag)

- avoid_tags (tags the visitor said no to, for example `رعب`)

- created_at
- updated_at

These conversation fields (audit 1.1) are filled by the assistant from what the visitor says; there
is no survey. They belong to the active session only: they are deleted with the session, never copied
to a guest or visitor profile, and never reported in analytics. Mobility is the one access need stored,
for its stated purpose (routes over accessible edges); no health detail is ever stored. Migration
`20261127110000_visitor_understanding` adds them with a CHECK
(`VisitorPreference_understanding_check`) on ages, list sizes and allowed values.

Do not store other accessibility or health details unless the product has explicit consent, a documented purpose, and a privacy review.

## Retention

Default policy for Phase 1:

- Active anonymous session: configurable, initially 24 hours after last activity.
- Visitor preferences: deleted with the session unless the visitor opts in.
- Remembered guests («تذكّرني»): deleted on request, when unticked, or after the same inactivity window as
  registered visitors. Link codes: 10 minutes; ended links are removed by `db:cleanup`.
- Registered visitors (optional feature): deleted after `WANEES_RETENTION_VISITOR_DAYS` (default 365)
  without a visit, or immediately on request; OTP challenges after 10 minutes; devices after 90 idle days.
- Aggregated operational analytics: retained according to the organizer contract.
- Raw audio: never retained by default.
- Full transcript: never retained by default.
- Audit logs: retained for security and operational needs.
- Crowd snapshots: 90 days by `observed_at`; removed only by the opt-in
  `db:retention` job, which is a dry run by default.
- Operator updates: 365 days by `created_at`, and only after the row ended or
  was revoked; a live update with no end and no revocation is never deleted by
  age. Deleting an update detaches any remaining linked snapshot
  (`ON DELETE SET NULL`).
- Expired records: removed by a scheduled job and excluded immediately from reads.

See [RETENTION.md](RETENTION.md) for the windows, environment variables, dry-run
output, batching, and the explicit `--apply` switch. The retention period must be
configurable per organization only after legal and product approval.

## Catalog publishing transaction

Publishing must be atomic:

1. Validate the draft.
2. Verify all referenced zones, activities, schedules, sources, and route edges.
3. Create the publish report.
4. Mark the old version superseded.
5. Set the event published_catalog_version_id.
6. Write an audit log.
7. Invalidate catalog cache.
8. Keep existing sessions pinned to their declared version.

If any step fails, the old published version remains active.

## Seed requirements

The seed command must create:

- One demo organization.
- One Boulevard World venue.
- One Boulevard World event.
- One published Boulevard World catalog version.
- One second small event with different zones and activities.
- One organizer account for local development only.
- Sample crowd snapshots marked simulated.

The second event is mandatory because it proves that the platform is not hard-coded to Boulevard World.

## Migration workflow

Every schema change must include:

- Prisma migration.
- Updated seed.
- Updated TypeScript types.
- Runtime validation.
- Unit or integration test.
- Documentation update.
- Recovery note for production-impacting changes.
