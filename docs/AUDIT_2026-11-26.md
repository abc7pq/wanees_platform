# WANEES audit — 2026-11-26

A full pass over every page, feature, API route, document and the visitor's journey, done
by reading the code, running the test suites and walking every visitor and organizer page in a
browser at phone (375 px) and desktop widths. This file records what was found, what was fixed,
and what is still open, in priority order.

## 1. Verdict

WANEES is a working product: a published multi-event catalog in PostgreSQL, a deterministic
planner, a grounded assistant that cannot invent prices or times, live crowd and delay
proposals the visitor accepts or declines, an organizer dashboard with roles and audit history,
and a CI pipeline that exercises the real HTTP flow. Its weak points were not the engine but the
edges: copy that still read like a hackathon entry, a few UX moments that broke trust (totals
lost on reload, an operator link visible to visitors, numbers in the wrong grammar), privacy
and abuse controls that were missing on the newest feature, and documentation that described
an older version of the product.

## 2. Positioning

### Who it is for

| Audience | What they buy | What WANEES proves today |
|---|---|---|
| Event organizers and venue operators (primary customer) | Visitor flow they can see and steer: fewer stuck crowds, help requests routed, a plan for every visitor | Organizer dashboard, crowd and delay broadcasts, help queue, catalog publishing with versions, analytics without visitor identities |
| Visitors (primary user) | «خمس أسئلة… ومسار ليلتك جاهز»: a night that fits their time, budget and party | Arabic-first guide, real catalog stops, reasons for every change, no account needed |
| Authorities and season programmes | Safe, privacy-preserving visitor guidance across many events | Multi-event isolation, retention jobs, deletion path, no raw chat storage |

### Recommended position

> **ونيس: طبقة الإرشاد الذكي للفعاليات.** The organizer publishes the event once; every visitor
> gets a personal, live plan; the operations room sees and steers the flow.

Lead with the organizer outcome (flow, safety, satisfaction) and show the visitor guide as the
proof. Three differentiators to repeat everywhere:

1. **Grounded, not generative.** Every price, time and walking minute comes from the published
   catalog and the engine; the model only explains. This is the answer to «what if the AI
   hallucinates?».
2. **The visitor decides.** Crowd and delay changes are proposals with a reason; only urgent
   closures apply automatically.
3. **Private by default.** Anonymous sessions, expiring assistant context, aggregated metrics.
   Registration is an organizer opt-in with SMS verification, consent and deletion.

### Landing page

- **Done in this round:** the landing page, its metadata and footer no longer present WANEES as
  «حل تحدي GEA في هاكاثون agentX». The phone mockups used 2025 activities that are not in the
  2026 catalog (فندق الفامباير, نقمة النيل), Eastern-Arabic digits, mood tiles that were not real
  quiz options, and «بدّل / ليس الآن» buttons. They now show real 2026 stops on their actual
  schedule (سكاي لوب 18:05 · 40, عرض الدولفيناريوم 18:30 · 65, تجربة الزرافات 19:25 · 50 ريال
  للشخص), the real first question «مين معك الليلة؟» with its four options, Western digits, and the
  real proposal buttons «اعتمد البديل / أبقي مساري».
- **Still open:** a short organizer section linking to the operations view.
- Keep the origin story (built during agentX for the GEA challenge) in the README's
  «نشأة المشروع» section, not in the product's title.

## 3. What was fixed in this round

### Visitor experience
- Party size and totals survive a reload; the rating prompt appears after the visit, not during.
- Destructive actions (reset plan, delete data) ask for confirmation.
- The operator link appears only on `/demo`; the service worker purges stale caches.
- Arabic count grammar (`app/lib/ar-count.ts`), no text under 12 px, removed jargon.
- Landing page: real 2026 mockups, and no hackathon framing in the title, description or footer.
- Walking directions before the visit now start «من البوابة» instead of naming the entrance
  zone as if the visitor were in it.
- Registration UX: clear consent, resend countdown, «لست أنا», «احذف بياناتي».

### Organizer experience
- Arabic labels throughout, activity picker grouped by zone, readable source labels.
- Help queue: open count, screen-reader announcements, lost-child reports first.
- Session expiry redirects to login instead of failing silently; database outages return 503
  with a clear message.
- Visitor list masks phone numbers; revealing one needs OWNER or ADMIN and is audited.
- Public demo credentials can only belong to a read-only account.

### Security and privacy
- SMS sending budget per phone, stored in the database (not per IP); organization-wide cap.
- Login-CSRF guard on OTP and device routes; constant-time token comparison; device cap per
  visitor; HMAC-scoped rate-limit keys.
- The test SMS provider works only on loopback and is refused in production builds unless
  explicitly allowed for CI.
- `db:cleanup` removes expired OTP challenges and devices, inactive registered visitors and
  stale guest profiles.
- Legacy `/api/session` and `/api/admin/broadcast` are rate-limited and validated; the
  in-memory session store is capped.
- Ambiguous public event slugs are refused instead of resolved by row order.
- Webook-sourced prices and verified-price markers removed (PR #7).

### Repository
- Unused admin routes and components, and about 5 MB of unreferenced media, removed.
- README rewritten around the product; documentation index, changelog and contributing guide
  added; hackathon documents archived; stale catalog counts corrected; seed source label fixed.

## 4. Open items, in priority order

|---|---|---|---|
| 1 | Organizer section on the landing page | Visitors see the guide; buyers need one block that shows the operations view | `app/app/page.tsx` |
| 2 | Per-person price label on each stop | Stop prices are per person while the budget is for the group; visitors can misread totals | visitor plan view |

| 5 | `recordVisitActivities` concurrent writes | Two tabs can race when recording a registered visitor's activities | `app/lib/visitor-store.ts` |
| 6 | Organizer user management and audit-log view | Audit history is stored but has no screen; users are created by seed or script | admin app |

| 8 | Analytics breakdowns (by zone, hour, party type) | The organizer story depends on showing flow, not totals | admin analytics |

## 5. How this was checked

- `npm test` in `app/` and `admin/`, `npm run test:contract`, app and admin `tsc --noEmit`, and
  both production builds.
- The registered-visitor flow end to end against a local server (`npm run test:visitors`).
- Every visitor page (`/`, `/demo`, `/ops`, `/ops/theater`) and organizer page walked in a
  browser at 375 px and desktop widths, in Arabic RTL.
- CI on each pull request runs the full PostgreSQL, HTTP, browser and load suites.
